1) System Overview (Architecture + Components)
============================================================
1.1 High-level Architecture
- Frontend (Clinic Center): `apps/web`
  - Next.js App Router
  - Server components for pages (data prefetch), client components for interactive workspaces.
  - Protected paths enforced in `apps/web/middleware.ts` (redirect to /login or /billing or /platform).

- Backend (Ops + business logic): `ops-dashboard`
  - Next.js internal API under `ops-dashboard/app/api/internal/*`
  - Domain logic under `ops-dashboard/lib/*`:
    - Conversations orchestration: `lib/conversations/processInbound.ts`, `bookingDialogueFlow.ts`
    - Scheduling: `lib/scheduling/slotService.ts`, availability engine, working hours guard
    - Emergency decisioning: `lib/scheduling/emergencyDecisionEngine.ts`
    - Billing lock: `lib/billing/localBilling.ts`
    - Audit trail: `lib/auditTrail.ts`

- Integration services:
  - WhatsApp transport: `whatsapp-bridge` (client/transport layer)
  - The “single source of truth” for reply logic is `ops-dashboard` (bridge can be configured to avoid duplicating routing menus).

1.2 Data Flow (Clinic Center → Ops Dashboard)
- User requests in `apps/web`:
  - Browser → Next middleware validates session cookie `ops_session`.
  - UI calls either:
    - Server-side data fetch (server components) via `apps/web/lib/ops-server.ts`, OR
    - Client-side fetch to BFF endpoints (`/api/ops/...`) using `fetchWithRetry`.

- BFF (apps/web):
  - `apps/web/lib/secure-api.ts` implements `callOpsApi(...)`:
    - Injects internal service token: `Authorization: Bearer ${SCHEDULING_SERVICE_TOKEN}`
    - Injects request correlation: `x-request-id`, `x-trace-id`
    - Injects tenancy:
      - `x-clinic-id` for clinic scope OR platform acting clinic.
      - `x-platform-scope: true` for platform sessions.
      - `x-user-id` from session.
    - Safety: for platform sessions, blocks non-GET writes unless a target clinic is specified (body clinic_id) or acting clinic cookie exists.

- Ops internal APIs:
  - Receive the service token + headers.
  - Must enforce authorization/tenancy based on `x-clinic-id` and/or explicit `clinic_id` query/body (critical for data isolation).

1.3 Database (Operational impact)
The Clinic Center surfaces touch these core tables (non-exhaustive):
- Tenancy/Clinic configuration:
  - `clinics`, `clinic_public_hours` (clinic hours), `staff_users` (admin accounts), clinic metadata JSONB
- Scheduling:
  - `doctors`, `doctor_working_hours`, `doctor_leaves`, `appointments`
- Conversations/CRM:
  - `conversations`, `conversation_messages` (or equivalent), `patients`
- Emergency + ops:
  - `cases`, `alerts`, `audit_logs`, `domain_events`, `core_outbox`
- Billing:
  - `clinic_local_subscriptions`, `clinic_payment_requests`, `billing_invoices`, `billing_receipts`, `billing_notification_log`

2.1 /dashboard — “لوحة أداء العيادة”
File: `apps/web/app/(app)/dashboard/page.tsx`

Purpose
- Executive snapshot for clinic operations:
  - patient count, today appointments, pending replies, active doctors, AI automation rate.

UI Elements
- Header:
  - AI handled % banner: derived from `fetchProductMetrics()`
- KPI cards: `KpiCards` (metrics computed from real rows)
- Charts/widgets: `ExecutiveCharts`, `DashboardWidgets`

UX Flow (step-by-step)
- Entry:
  - If platform superadmin without acting clinic → shows a blocking card “اختر عيادة من Platform Switcher”.
- Otherwise:
  - Prefetch (server-side):
    - Inbox rows, patients, upcoming appointments, product metrics.
  - Render KPIs:
    - totalPatients: `patients.length`
    - pendingReplies: inbox rows where status === "open"
    - activeDoctors: unique doctor_id from appointments
    - todayAppointments: computed from starts_at date equality to local browser date (see risks below)
    - aiSavedHours: derived from aiHandled / 12 heuristic (NOT a “fake number”, but a derived metric; still should be validated as acceptable).

Expected Validation Rules
- If any upstream fetch fails:
  - Page still renders (empty arrays), but KPIs degrade silently.
  - Recommendation: show “data unavailable” states per widget when fetch fails (see “Bugs/Risks”).

Potential Failures / Edge Cases
- Timezone mismatch:
  - `todayAppointments` uses `new Date(a.starts_at).toDateString()` vs `new Date().toDateString()` which uses server runtime timezone (server component) at build-time request.
  - If clinic timezone differs, “today” can be wrong.
- Product metrics are global (not necessarily clinic-specific):
  - Could mislead if metrics aggregate across all clinics (depends on ops implementation).

APIs
- Internal fetch via `apps/web/lib/ops-server.ts`:
  - GET `/api/internal/inbox?clinic_id=...`
  - GET `/api/internal/patients?clinic_id=...`
  - GET `/api/internal/appointments/upcoming?clinic_id=...&days=...`
  - GET `/api/internal/metrics/product`

DB Impact
- Read-only.

- Main panel:

  - reply textarea
  - actions:
    - send reply
    - choose template key
    - AI suggest
    - decision timeline panel (auditability)
    - execute suggested action
    - feedback modal/panel (correct decision + severity + medical signals + patient context)
    - doctor assignment (select)

UX Flow (step-by-step)
- Initial load:
  - Server selects first conversation from inbox list and fetches detail+messages.
  - Client workspace receives:
    - `rows`, `selectedId`, `detail`, `messages`
- Triage behavior:
  - Sorting uses rank:
    - confirmed emergency → top
    - uncertain emergency
    - unread
    - rest by last_message_at
- Operator actions:
  - Reply:
    - validate non-empty text
    - POST to `/api/ops/conversations/[id]/reply`
  - Template:
    - GET template or apply template (BFF endpoint exists)
  - AI Suggest:
    - calls `/api/ops/conversations/[id]/ai-suggest` (exists)
  - Execute decision:
    - `/api/ops/decision/execute`, `/api/ops/decision/regenerate`, `/api/ops/decision/feedback`
  - Conversation actions:
    - `/api/ops/conversations/[id]/actions` for archive/close etc (exists)

Validation Rules (expected)
- Reply: non-empty trimmed text.
- Feedback:
  - correctedDecision in {EMERGENCY, BOOKING, NORMAL, UNKNOWN}
  - correctedSeverity numeric string → should be 1..5 or similar (not fully enforced client-side; verify server-side schema).
- Assign doctor: must be a known doctor id; enforce server-side.

Functional Risks / Race Conditions
- Concurrency:
  - Two agents replying simultaneously can interleave messages; require idempotency keys (present in API).
  - Suggested action execution may become “blocked” if appointment already exists or slot unavailable; UI already localizes blocked reasons.
- Stale data:
  - Server prefetched detail for first conversation; client actions may mutate state without full refetch unless router.refresh is used consistently.
- Deterministic UX:
  - Uses Radix Select/Tabs in multiple places; historically can break in some browser/layout combinations (aria-hidden focus trap). If this happens inside Inbox it becomes a critical operational blocker.

APIs (BFF in apps/web/app/api/ops/*)
- Conversations:
  - POST `/api/ops/conversations/[id]/reply`
  - GET/POST `/api/ops/conversations/[id]/template`
  - POST `/api/ops/conversations/[id]/ai-suggest`
  - POST `/api/ops/conversations/[id]/actions`
- Decisions:
  - POST `/api/ops/decision/execute`
  - POST `/api/ops/decision/regenerate`
  - POST `/api/ops/decision/feedback`
- Doctors list for assignment:
  - GET `/api/ops/doctors`

DB Impact (ops-dashboard side)
- Read/write:
  - `conversations`, `conversation_messages` (reply insertion)
  - `appointments` (if executing booking)
  - `audit_logs` + `domain_events` for traceability

4) API & Backend Mapping (Concrete paths + payload patterns)
============================================================
4.1 BFF pattern (apps/web)
- Client UI calls `/api/ops/...` with session cookies.
- BFF checks session with `/api/auth/me` (cookie-based).
- BFF proxies to ops-dashboard internal API using service token + x-clinic-id header.

4.2 Example APIs (from inspected routes)

A) Appointments availability
- UI: `AppointmentsBoard.checkAvailability()`
- Request: POST `/api/ops/appointments/availability`
  - body: { doctor_id: number, specialty?: string, conversation_id?: number, limit?: number }
- BFF handler: `apps/web/app/api/ops/appointments/availability/route.ts`
  - forces `clinic_id = user.clinic_id`
  - proxies to internal scheduling slots via `fetchDoctorSlots(...)`
- Expected response:
  - { ok: true, slots?: [...], reply_lines?: string[], closed_message_ar?: string }
  - failure: { ok: false, error: string }

B) Create appointment
- UI: `AppointmentsBoard.createBooking()`
- Request: POST `/api/ops/appointments/create`
  - body: { doctor_id, patient_id, starts_at, conversation_id?, idempotency_key? }
- BFF: `apps/web/app/api/ops/appointments/create/route.ts`
  - forces clinic_id from session
  - proxies to internal confirm endpoint
- Response:
  - ok + appointment_id or duplicate + error/code

C) Clinic settings

6) Bug Detection (Critical) — Issues Likely Before Production
============================================================
6.1 UI/UX Bugs (high priority)
- Settings “fake data flashing”:
  - `SettingsTabs` renders hardcoded defaults before API returns.
  - Impact: violates “No fake data” perception; can confuse operators.
  - Fix: render skeleton until GET completes; defaultValues should be empty.

- Appointments non-functional buttons:
  - “تصدير” and “حجز سريع” appear without handler in read window.
  - Impact: dead buttons reduce trust.
  - Fix: wire to real export endpoint or disable with tooltip “غير متاح حالياً”.

- Appointment calendar hours are static:
  - Grid fixed to 9..17; does not respect clinic/doctor hours.
  - Impact: operators may believe clinic is unavailable.
  - Fix: drive slots grid from clinic_public_hours / doctor_working_hours.

- Patients list scalability:
  - limit=150 hard cap in server fetch.
  - Impact: real clinics will exceed; search becomes misleading.
  - Fix: server-side pagination + search endpoint.

6.2 Logic Bugs / Correctness
- “Today” computations:
  - dashboard uses server runtime date; clinic timezone can differ.
  - Fix: compute “today” using clinic timezone from settings.

- Platform vs clinic writes:
  - BFF blocks platform writes without target clinic or acting clinic cookie (good).
  - Risk: some endpoints may accept `clinic_id` in body and override header; must standardize precedence.

6.3 Security Issues (AuthZ / Data leakage)
- Service token pattern:
  - apps/web uses a powerful internal token for all ops calls.
  - Security relies on:
    - strict validation in ops-dashboard internal APIs of x-clinic-id/x-platform-scope
    - not trusting client-provided clinic_id
  - Failure mode: a single internal API that trusts client body `clinic_id` could lead to cross-tenant data access.
  - Recommendation: enforce tenancy only from headers, ignore body clinic_id except in platform-controlled endpoints with permission checks.

- Support endpoints exposure:
  - /support is available even when billing_locked (middleware allows).
  - Ensure support data is scoped properly and not exposing other clinics when platform scope is used.

6.4 Performance bottlenecks
- Inbox workspace:
  - Potentially heavy: lots of state, decision timeline building, large messages list.
  - Risk: slow rendering for long threads; needs virtualization and paging for messages.
