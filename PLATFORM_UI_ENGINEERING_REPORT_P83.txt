================================================================================
1) Executive Summary
================================================================================
This codebase now has a dedicated Platform Console for platform-scoped users (primarily super_admin, plus ops_admin/ops_manager when enabled).

Platform Console goals:
- Keep super_admin in a platform-first cockpit (no clinic shell by default).
- Provide global visibility: clinics, revenue, support, search, alerts, audit, and growth.
- Provide safe global control: lifecycle actions (suspend/activate/plan/owner/trial-days) and clinic context switching.

Current status:
- Platform routes exist and build cleanly (apps/web build + ops-dashboard build).
- Platform navigation is separated from clinic navigation.
- Platform pages fetch via BFF routes in apps/web, which proxy to ops-dashboard internal APIs.
- Platform writes are guarded (super_admin scope required for BFF write routes).

================================================================================
2) System Architecture (High-level)
================================================================================
Components:
1) apps/web (Next.js 14 app) — "SaaS Web + Platform Console" (Port 3000)
   - Contains UI pages for clinic scope and platform scope.
   - Contains BFF endpoints under /api/* that proxy to ops-dashboard internal APIs.
   - Enforces session/scope rules in middleware and API guards.

2) ops-dashboard (Next.js 14 app) — "Ops + Internal APIs" (Port 3001)
   - Contains /api/internal/* endpoints that implement data and operational actions.
   - Contains auth login with special handling for super_admin (2FA + IP allowlist).
   - Contains DB access and audit log writes.

3) whatsapp-bridge — messaging bridge + shared DB migrations

Platform Console data flow:
Browser -> apps/web (UI page) -> apps/web (BFF /api/platform/* or /api/ops/*)
-> ops-dashboard (/api/internal/*) -> DB

Mermaid flow:

flowchart LR
  Browser -->|UI requests| WebApp[apps/web]
  WebApp -->|BFF proxy| Ops[ops-dashboard]
  Ops -->|SQL queries| DB[(Postgres)]

4) Authentication, Session, and Scope Model
================================================================================

4.1 JWT/session fields
ops-dashboard signs ops_session JWT with payload:
- role
- scope: "clinic" | "platform"
- clinicId (only for clinic scope)
- billingStatus/billingLocked hints

File:
- ops-dashboard/lib/jwt.ts

4.2 Login behaviors
File:
- ops-dashboard/app/api/auth/login/route.ts

Rules:
- Regular clinic users: scope=clinic, clinicId set, billing snapshot computed.
- super_admin:
  - Forced security checks:
    - IP allowlist enforced
    - MFA/TOTP enforced
  - Token scope becomes platform (scope=platform) when platform scope is enabled.
- Delegation (P8.3 enhancement):
  - ops_admin and ops_manager can also receive scope=platform IF:
    - staff_users.security_flags.platform_scope === true
  - This enables delegated platform access without using super_admin.

4.3 apps/web session parsing
File:
- apps/web/lib/webAuth.ts

Behavior:
- Accepts platform scope sessions (clinic_id becomes 0 for platform).
- Previously platform acceptance was restricted to super_admin; now any scope=platform is treated as platform session.

4.4 Session endpoint (apps/web)
File:
- apps/web/app/api/auth/me/route.ts

Behavior:
- If sessionScope === "platform": returns clinic_id=0 and billing unlocked.
- Otherwise: attempts to validate billing lock via ops-dashboard /api/auth/billing-lock.

- /api/platform/clinics/[id]/lifecycle (BFF)

- activate: sets status='active' (and renewal defaults)

- set_owner: updates clinics.metadata owner fields

Security:
- BFF requires requireUserSession + role super_admin + scope platform.
- ops-dashboard internal lifecycle requires x-platform-scope header true.

9) Security Engineering & Guardrails
================================================================================

9.1 super_admin security (ops-dashboard)
- IP allowlist required:
  - user_ip_allowlist entries must match request IP
- MFA required:
  - user_mfa_secrets must exist and otp_code must verify

Files:
- ops-dashboard/app/api/auth/login/route.ts
- whatsapp-bridge/sql/migrations/036_super_admin_security.sql
- ops-dashboard/scripts/seed-super-admin.cjs
- ops-dashboard/scripts/super-admin-allowlist.cjs

9.2 Platform writes safety
- All platform write actions currently routed through:
  - apps/web BFF routes that check platform session and super_admin role
  - ops-dashboard internal routes that require x-platform-scope=true (scheduling service token auth)

9.3 Multi-tenancy protections
- Tenant-scoped endpoints require clinic_id, and platform global mode avoids them.
- Hardcoded clinic_id=1 in manual billing UI was removed earlier (P8.2).

11) Known Limitations / Remaining Work (Engineering Gaps)
================================================================================

Clinics lifecycle coverage (current implementation):
- Implemented: suspend, activate, trial_days, plan, owner metadata.
- Not yet implemented:
  - clinic deletion (safe delete)
  - change staff ownership user row (transfer admin user)
  - quotas/limits enforcement UI (doctors_count vs plan limits)

Growth analytics:
- Phase 1 uses trial funnel and billing summary counts only.
- No CAC/LTV, no cohort retention, no churn root-cause analysis yet.

Alerts:
- Phase 1 is UI aggregation of existing endpoints.
- No alert routing/escalation policies, no persistence/ack state.

Audit Explorer:
- Phase 1 viewer.
- Needs richer filters (actor, action, time range), export, and IP/session context display if available.

Delegation:
- Platform scope enabled by security_flags.platform_scope for ops_admin/ops_manager.
- Fine-grained RBAC per module (Support-only vs Billing-only) is not yet enforced at UI/action level.

================================================================================

- apps/web on 3000
- ops-dashboard on 3001

- Confirm platform sidebar entries visible

3) Clinics actions:
- /platform/clinics

4) Alerts:
- /platform/alerts
- Confirm health + failures + billing summary load

5) Audit:
- /platform/audit
- Try clinic_id=0 (all) then a specific clinic id

6) Growth:
- /platform/growth
- Confirm trial funnel endpoint returns data

7) Search:
- /platform/search
- Query by phone/name and verify results and "Enter clinic" action.
